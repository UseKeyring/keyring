# Keyring access notes

- Monorepo (bun + turbo, rebase-style): `apps/web` is the Next.js app, `packages/cli` (`@usekeyring/cli`, bin `keyring`) is the CLI — `keyring dev` = PGlite local Keyring + console (`src/studio.html`) + hosted-compatible `/api/v1`; targets resolve `--base-url`→hosted, `DATABASE_URL`→native schema, else `.keyring/`; policy-as-code in `keyring.policy.json`; built with `bun run scripts/build.ts` (bundles sdk+mcp, ships `drizzle/native.sql` as `dist/native.sql`); run in-repo via `bun keyring <cmd>`. Embedded SDK mode `@usekeyring/sdk/postgres` (`createKeyring({ database, apiKey })`) calls `keyring.api_*` RPCs directly. Local mode `@usekeyring/sdk/local` (`createKeyring({ policy, store? })`, zero deps, no DB) is an in-process engine with native.sql semantics, kept honest by `packages/cli/src/parity.test.ts` (PGlite); `jsonFileStore` lives at `@usekeyring/sdk/local/file`. `packages/ui` (`@keyring/ui`) is the shared component library, `packages/sdk` (`@usekeyring/sdk`) is the integrator TypeScript client for `/api/v1` (server secret + browser publishable), `packages/typescript-config` (`@keyring/typescript-config`) holds base/nextjs/react-library tsconfigs. Workspaces: `apps/*`, `packages/*`. Run `bun install`, `bun dev` / `bun run build` (turbo), per-app `bun --filter @keyring/web dev`, SDK `bun --filter @usekeyring/sdk build`.
- UI rule: all shared components live in `packages/ui/src/components/*`, utils in `packages/ui/src/lib/utils.ts`, `useIsMobile` in `packages/ui/src/hooks/use-mobile.tsx`, design tokens in `packages/ui/src/styles/globals.css` (single source; `apps/web/src/app/globals.css` just re-exports it). Import in app as `@keyring/ui/components/<name>`, `@keyring/ui/lib/utils`, `@keyring/ui/hooks/use-mobile`. shadcn aliases live in `packages/ui/components.json`. `AvatarUpload` in UI is storage-agnostic (`uploadFile` prop); the Supabase "Avatars" bucket injection lives in `apps/web/src/components/avatar-upload.tsx`.

- Database: `drizzle/schema.sql` is the squashed full schema for FRESH projects (equivalent of 0000–0013). Migrated DBs keep applying `drizzle/migrations/` incrementally — never run the squash on them. Apply via the Supabase SQL editor (each file is idempotent) or `supabase db push`; `drizzle-kit`/`drizzle-orm` were removed — there is no `drizzle.config.ts` and no ORM layer.
- Multi-workspace: accounts hold many workspaces via `organization_members`; `profiles.organization_id` is the ACTIVE one (drives URLs `/dashboard/[orgSlug]` + all RLS). Switch with `switch_organization`, leave/remove with `remove_member` (revokes that workspace's console grants, repairs active). Console grants (`member_roles.organization_id`) and the creator bypass are scoped to the active workspace. `typedRoutes` is off — workspace URLs are dynamic by design.
- Next.js App Router (`src/app`). Client components carry `"use client"`.
- Supabase browser client: `src/integrations/supabase/client.ts` (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`).
- Supabase server client: `src/integrations/supabase/server.ts` (user sessions).
- Management API (`apps/web/src/app/api/v1/`) runs over the Supabase publishable key only — no service_role anywhere. Issued keys: **secret** `kr_sk_live_…` vs **publishable** `kr_pk_live_…` (legacy `kr_live_…` = secret). Capabilities come from `api_keys.scopes` (built-in Management API scopes: `check`, `grants.write`, `roles.read`, `roles.write`, `spaces.read`, `spaces.write`, `actions.read`, `actions.write`, `subject_tokens.write`, plus `telemetry.read`/`telemetry.write`) — Polar-style picker in Settings; publishable keys are capped to `check` (+ subject JWT). Key type in `0027_api_key_types.sql`; scopes + expiry in `0028_api_key_scopes.sql`; role/action writes (`api_create_role`, `api_create_permission`) in `0033_role_action_writes.sql`. Bootstrap order key-first: `POST /api/v1/permissions` → `POST /api/v1/roles { permissions }` → `POST /api/v1/grants`. Subject tokens signed with `SUBJECT_TOKEN_SECRET` (`apps/web/src/lib/subject-tokens.ts`, `jose`). Integrator client: `@usekeyring/sdk`.
- Billing (Polar MoR): creating a workspace requires an active Pro/Enterprise row in `user_subscriptions` — enforced by RLS (`subscribed create organizations`, 0010) with a friendly client pre-check in `createOrganization`. Self-hosters stay free. Flow: `polar-checkout` edge fn → Polar checkout (metadata carries `supabase_user_id` + `plan_code`) → `polar-webhook` verifies the Standard Webhooks signature, dedups raw events into `billing_webhook_events`, upserts `billing_customers`, syncs via `sync_subscription`. `polar-portal` opens the customer portal. Client: `useMySubscription` / `usePolarCheckout` / `useCustomerPortal` (`src/hooks/useBilling.ts`); billing UI lives on the account page. Deploy: `supabase functions deploy polar-checkout polar-webhook polar-portal` with secrets POLAR_ACCESS_TOKEN, POLAR_ENV, POLAR_PRO_PRODUCT_ID, POLAR_WEBHOOK_SECRET, APP_URL. Webhook URL for the Polar dashboard: `https://<project>.supabase.co/functions/v1/polar-webhook`.
- Service-role exception: the Next.js stack stays publishable-key-only, but the three billing edge functions use SUPABASE_SERVICE_ROLE_KEY (server-side secret, never shipped to the browser) because webhooks arrive with no user session.
- RBAC model: console accounts (auth/profiles) operate the workspace and are NOT in the graph. Subjects (external end-users) hold grants of roles composed of actions. Console access derives from console-scope roles via member_roles (owner = org creator bypasses all); `useMyAccess().can()` resolves slugs through the `my_console_permissions()` SECURITY DEFINER function because the RBAC tables are read-gated. Manage permissions imply their read counterpart (`roles.manage` → `roles.read`, etc.).
- Membership: joining requires an approved row in `organization_join_requests` — request by slug (`request_to_join_org`), approve/reject by org managers (`decide_join_request`, creator or users.manage/organizations.manage holder of THAT org). Direct `profiles.organization_id` writes are blocked by the `guard_profile_org_change` trigger except self-leave, self-link as org creator, manager unlink, and the approve function (bypass flag).
- Design system: ASCII system. Tokens live once in `apps/web/src/app/ascii-tokens.css` (`--a-*`, paper/charcoal, one burnt-orange accent, grain via `--a-noise`), fonts once in `ascii-fonts.ts` (Inter Tight display + JetBrains Mono). Public pages compose `ascii-shell.tsx` (`AsciiPage`, `Row` railed frames, `Nav`, `Footer` with the canvas `ascii-field.tsx`) + primitives in `ascii.css` (`.cells` shared-border grids, `.btn` 2px blocky, `.win`, `.notice`, `grain`/`hatch`/`dots`); isometric illustrations via `iso.tsx` kit (`hero-illustration.tsx`, `illustrations.tsx`). Console: `dashboard/console-scope.tsx` puts `ascii-console` on <html> (so Radix portals inherit) and `console.css` remaps the Polar tokens of `packages/ui` onto `--a-*`. Docs: `app/docs/docs.css` (`.ascii-docs`) remaps fumadocs vars; `source.config.ts` exposes code-fence language. Legacy Polar tokens in `packages/ui` still exist underneath.
- Backups: 7-day backup system with automatic daily backups. Setup: Apply migrations `0015_backups.sql` and `0016_backup_storage.sql` via Supabase SQL editor. Deploy edge functions: `supabase functions deploy backup-create backup-restore backup-list backup-scheduled` with secrets BACKUP_CRON_KEY (for scheduled backups). Storage bucket "backups" is created automatically. Manual backup creation and restore available in workspace settings for org managers (backups.manage permission).
